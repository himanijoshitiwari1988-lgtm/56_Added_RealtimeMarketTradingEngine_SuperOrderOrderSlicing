2) BB%b ENGINE RUN WINDOW (AST only) - a new BB%b control in the AST BB%b alert
   section that AUTO-STARTS / AUTO-STOPS the engine run between two BB%b lines,
   using the same "two alert lines" UI pattern the BULL CE / BEAR PE rows use
   (each line = crossed_above/crossed_below dropdown + value input moved up/down
   to set). Defaults: ACTIVE = crossed above 0.8, INACTIVE = crossed below 0.2.
   Semantics: the engine only allows NEW entries inside the window - it starts
   from the first BB%b ACTIVE crossing and stops at the BB%b INACTIVE crossing.
   Open trades keep running to their SL/TP/trail the whole time (only the
   entry side is paused). When the window is ON a fresh run always starts
   dormant/INACTIVE and waits for the ACTIVE line crossing.
   - static/niftybbp_alert.js: win config {enabled, active{...}, inactive{...}}
     persisted under localStorage <pfx>BbpWinCfg (astBbpWinCfg); crossing-based
     latch stepWindowState() advanced inside feed() on the same prev/last sample
     pair the BB%b alerts fire from; seedWindowState() on attach/enable (seeds
     ACTIVE only when BB%b is already past ACTIVE and not past INACTIVE, else
     dormant); windowReset() (forces INACTIVE, no-ops when window off),
     windowStatus(), setWindowEnabled(), editWinDraft() (values clamped
     ALERT_MIN..ALERT_MAX), paintWindowChip() (chip <pfx>BbpWinState shows
     "RUN ACTIVE/INACTIVE"), syncWinEditor/syncWinEditorRow for the editor
     rows. All exported on window.NiftyBbpAlert. Extra attach() state: winKey,
     win, winState; reset() re-seeds the window on a timeframe change.
   - static/aismart.js: new bbpWindowBlock() helper returns a block reason when
     the window switch is ON and the window state is INACTIVE (and null when OFF
     or ACTIVE) - a higher-level pause/resume latch layered ABOVE the existing
     BB%b alert gate (bbpGateBlock) so an INACTIVE window stops entries
     regardless of the gate state. Called immediately before bbpGateBlock at
     both AST entry seams: the HFT scanner path and the normal poll path (which
     also carries the Indicator-filters runs), so an INACTIVE window keeps the
     engine dormant while the open-position/trail/SL-TP management loop keeps
